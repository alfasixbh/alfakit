# Stability and upgrades

AlfaKit is one product shipped as several packages: `alfasix/alfakit` on Composer and `@alfakit/core`, `@alfakit/react`, `@alfakit/vue` and `@alfakit/svelte` on npm. They are released together and share one version number. Within a major version an upgrade should never break an application; this page says exactly what that promise covers.

## What semantic versioning covers

Breaking changes to any of the following only happen in a new major version. Until then they may gain features (minor) or fixes (patch), never lose or change behaviour you rely on.

| Covered               | Examples                                                                                                                                                                                                                                                                                                             |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The fluent PHP API    | Public methods of panels, resources, pages, schema components, fields, entries, columns, filters, actions, widgets, notifications and plugins (`TextInput::make()->live()`, `Table::recordActions()`, `Panel::plugin()`…), and their closure arguments (`$record`, `$state`, `$get`, `$set`, `$operation`, `$model`) |
| The schema contract   | The JSON produced by `toSchema()` and typed in `@alfakit/core` (`packages/core/src/schema`). Props are only added within a major; a renderer ignores unknown props                                                                                                                                                   |
| Internal endpoints    | The `/_alfakit/*` routes, their request and response shapes, and the `SchemaContext` token protocol                                                                                                                                                                                                                  |
| Registry keys         | Component type strings (`TextInput`, `Section`…) and the reserved keys renderers resolve (`layout:app`, `layout:auth`, `layout:blank`, `panel:sidebar`, `panel:topbar`, `panel:impersonation-banner`, `widget:*`…)                                                                                                   |
| Theme hooks and slots | `data-slot` and `data-*` attributes documented in [Design](../design/themes), the CSS variables of `@alfakit/core/themes.css`, `data-alfakit-theme`, and the named `<Slot>` positions (`page.header.before`, `page.actions.before`…)                                                                                 |
| Frontend entry points | `createAlfakit()`, `createAlfakitServer()`, `<AlfakitComponent>`, the hooks exported by each renderer (`useT()`, `useFormatter()`, `usePanel()`…) and the exports of `@alfakit/core`                                                                                                                                 |
| Artisan commands      | Command names and their documented arguments and options                                                                                                                                                                                                                                                             |
| Translation keys      | Keys in `alfakit::ui` and the other `alfakit::*` groups; a renamed key keeps the old one as an alias for the rest of the major                                                                                                                                                                                       |

## What it does not cover

- **Renderer internals.** The file layout of `packages/react/src`, `packages/vue/src` and `packages/svelte/src`, the shadcn primitives in `components/ui`, class names on elements without a `data-slot`, and any export not listed in the package's `index.ts` are implementation details. Copy a component into your project if you need to change it; don't import from a deep path.
- **Protected and private PHP members.** Extending a class and overriding a protected method keeps working within a patch release, but protected signatures can change in minor releases when a feature needs it. Prefer `configureUsing()`, closures and the public API.
- **Generated code.** The stubs behind `make:alfakit-*` evolve; files generated by an older version keep working because they only use the public API, but they are not updated for you.
- **The playgrounds and documentation site.**
- **Behaviour reached through a bug.** A fix that changes behaviour the documentation never promised is a patch.

## The schema contract version

The contract has its own version, separate from the package version, so a renderer can tell whether it understands the JSON a server sends:

- PHP: `AlfaSix\Alfakit\Support\SchemaContract::VERSION` (shared with every page as `alfakit.schemaContract`).
- Frontend: `SCHEMA_CONTRACT_VERSION` from `@alfakit/core`.

The major part changes only when a prop is removed or changes meaning; the minor part when props are added. On every page the renderers compare the major parts (`checkSchemaContract()`); when they differ, the page is replaced by a translated message (`ui.schema_contract.title` / `ui.schema_contract.body`) and `console.error` names both versions once, instead of rendering half-broken UI. A server that sends no version (older than 1.0) is treated as compatible. `alfakit:upgrade` reports the same comparison for the `@alfakit/*` packages in your `package.json`.

## Deprecation policy

A feature is never removed in the release that deprecates it.

1. **Announced** in a minor release: the changelog lists the deprecation and its replacement, the API's docblock gets `@deprecated`, and, where it can be detected at runtime, calling it reports a warning (below). The old behaviour keeps working for the rest of the major version.
2. **Removed** in the next major release, listed in the upgrade guide of that version.

Runtime warnings are reported once per process, so a long-running worker or an Octane server logs each deprecation a single time:

- **PHP**: `Deprecations::warn('Table::actions()', 'use recordActions() instead', since: '1.2')` (`AlfaSix\Alfakit\Support\Deprecations`) writes a `warning` through the application's logger (`[Alfakit] Table::actions() is deprecated since Alfakit 1.2: use recordActions() instead`, with `alfakit: deprecation` in the context) and collects it. `Deprecations::all()` returns the list for this process and `Deprecations::toDebug()` returns it only when `app.debug` is on: that is the `deprecations` list of the debug panel. `Deprecations::flush()` forgets them (tests, queue workers). Commands invoked through a legacy alias (`alfakit:make-theme` instead of `make:alfakit-theme`) report this way and also print a warning.
- **Frontend**: `deprecate('createAlfakit({ adapters })', 'pass components instead', { since: '1.2' })` from `@alfakit/core` writes one `console.warn` per key; `reportedDeprecations()` lists them and `resetDeprecations()` clears the list.

To find deprecations in your application, search your logs for `[Alfakit]`, open the debug panel in development, or run your test suite with the logger set to fail on `warning` entries.

## Upgrading

Within a major version:

```bash
composer update "alfasix/*"
npm update @alfakit/core @alfakit/react   # or @alfakit/vue, @alfakit/svelte
php artisan alfakit:upgrade
npm run build
```

`"alfasix/*"` updates the first-party plugins with the core package: they are released with it, and `composer update alfasix/alfakit` alone leaves them on their old version.

Add `@php artisan alfakit:upgrade` to the `post-autoload-dump` scripts of `composer.json` so it runs after every update. The command clears AlfaKit's caches and compiled views, republishes plugin assets, and prints a compatibility report:

- every installed Composer package that declares [`extra.alfakit`](../panels/plugins#declaring-compatibility) is marked **compatible**, **incompatible** or **unknown** against the installed `alfasix/alfakit` version (and its declared frontend package against the plugin's own version);
- every `@alfakit/*` package in `package.json` is compared with the PHP package's major version (for `0.x` releases the minor must match too).

The report never blocks the upgrade. With `--strict` the command exits with code 1 when anything is incompatible, which is what you want in CI:

```bash
php artisan alfakit:upgrade --strict
```

It also points out published views, stubs and translation overrides that may need a look, and reminds you to run `php artisan optimize` when routes or configuration are cached.

To a new major version: read that version's upgrade guide first, update the Composer and npm packages to the same major, run `alfakit:upgrade --strict` and fix what it reports, rebuild the frontend, and then address the deprecations removed in that major. Keep the PHP and npm packages on the same major at all times; the schema contract check exists exactly to make a mismatch obvious.
